FraudCast

UPI Transaction Fraud Detection — Project Report
Author: Vineet Hankare Date: June 2026 Repo: github.com/v1neet3/FraudCast (private)

Abstract

FraudCast is an end-to-end machine learning system for detecting fraudulent UPI (Unified Payments Interface) transactions on personal financial data. The system combines anomaly detection, physics-based location verification, and an ensemble classifier into a unified three-stage pipeline. A FastAPI backend serves model predictions in real time, and a React dashboard provides both interactive transaction scoring and a browsable history of all flagged transactions.

At threshold 0.30 the system achieves 95% recall on synthesized fraud with an average fraud score of 0.169 across 779 scored transactions.

Motivation

Consumer UPI fraud is rising in India — phishing, SIM swaps, and merchant impersonation are common attack vectors. Individuals have no transparent tool to understand why a transaction was flagged or to score transactions proactively. FraudCast was built to fill this gap using only a personal Google Pay export, with no dependency on external APIs or cloud services.

Fraud Synthesis

80 synthetic fraud transactions were injected using four realistic attack patterns:

PatternShareMechanism
amount_spike30%Amount set to 6–15× the domain average
location_jump25%GPS teleported to Delhi or Bangalore with only 15–60 min gap
off_hours25%Transaction time rewritten to 1:00–5:59 AM
new_recipient20%Payee replaced with unknown vendor, amount ₹800–3,500

Each synthesized row inherits all other fields from a randomly sampled real transaction to preserve plausible metadata. Final dataset: 779 transactions — 699 Legit + 80 Fraud.

Feature Engineering

13 features are computed per transaction using an expanding window — each row only sees data from prior transactions, eliminating look-ahead leakage. Domain statistics are computed exclusively on Legit training data.

Pipeline Architecture

The pipeline runs three sequential stages. Each produces a score in [0, 1]; the weighted sum is the final fraud score:

fraud_score = 0.25 × IF_score  +  0.20 × LOC_score  +  0.55 × CLF_score

+
Location Check
20%

55%

Stage 1 — Isolation Forest

Trained exclusively on Legit transactions using 5 features: amount_zscore, amount_ratio, hour, is_night, txn_count_1h. The raw decision function is min-max normalised and inverted so higher values = more anomalous. Contamination = 0.10.

Stage 2 — Location Check (Haversine)

Implied travel speed between consecutive transactions is computed offline using the Haversine formula:

speed (km/h) = distance_km / (time_gap_min / 60)
LOC_score    = min(speed / 150, 1.0)

A ceiling of 150 km/h is used. A transaction implying 450 km/h travel (e.g. Mumbai → Delhi in 2 hours) scores 1.0 — physically impossible without air travel and a matching time gap.

Stage 3 — Adaptive Weighted Fusion (AWF)

ClassifierRole
GradientBoostingClassifier (100 trees)Primary classifier — captures feature interactions
GaussianNBFast probabilistic baseline
SVC (RBF kernel, probability=True)Strong decision-boundary classifier

Each classifier is weighted by its accuracy on a held-out 20% validation split of the SMOTE-resampled training data:

weight_i      = accuracy_i / Σ accuracy_j
clf_score(x) = Σ weight_i × P(fraud | x)_i

Training Strategy

Time-based Split

A strict temporal split is used — no random shuffling. Shuffling would leak future transaction patterns into the past and inflate metrics.

SplitCutoffTransactionsFraud
TrainBefore 2023-07-0140940
TestAfter 2023-07-0137040

Class Imbalance — SMOTE

The raw training set is ~9:1 Legit:Fraud. SMOTE generates synthetic minority samples in feature space on the training split only, producing a balanced dataset for the AWF classifier without duplicating real rows or leaking test data.

Evaluation & Threshold Tuning

0.353895.0%1473.1%

Rationale: 0.30 and 0.35 achieve identical recall. The 15 additional false positives at 0.30 are acceptable for a personal monitoring tool — missing real fraud is costlier than a false alert. Moving to 0.25 gains one extra fraud catch at the cost of doubling false positives without meaningful recall improvement.

Limitations

  • Synthetic fraud only — four patterns are covered; novel attack vectors may score low
  • No live GPS — coordinates were added manually per merchant; the location check is most useful with real-time GPS
  • Static domain stats — mean/std are fixed at training time; new merchant categories fall back to global defaults
  • No persistence — models are retrained from scratch on every server start (~20–30 s)

Future Work

  • Online learning — incremental domain stat updates as new transactions arrive
  • Real fraud labels — integrate with bank dispute records to replace synthesized cases
  • Push alerts — score transactions automatically via UPI webhook or periodic statement fetch
  • Model persistence — serialise trained artefacts with joblib for instant startup
  • Dashboard export — PDF/CSV download of flagged transactions
